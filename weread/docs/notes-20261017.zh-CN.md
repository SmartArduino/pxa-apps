## 官方接口与功能边界

依据 [Tencent/WeChatReading 1.0.5 的笔记说明](https://github.com/Tencent/WeChatReading/blob/d98e66ee60a8c7bcd35da549d0643c4470439643/skills/notes.md)，复用已有网页会话，只读获取已经存在的 Skill Key，再向固定官方网关发送 Bearer 请求。未创建或重置 Key；网关 Cookie 不进入网页会话，网页 Cookie 不发送给网关或图片站。Key 只随本次请求存在，不写入文件或日志。

| 能力 | 请求及实现 |
|---|---|
| 划线 | `/book/bookmarklist`，参数 `bookId`；接口未定义分页，接收有界响应后每次显示十条，换窗口时重新获取，避免默认缓存全量模型 |
| 个人想法 | `/review/list/mine`，参数为小写 `bookid`、`count=10`、`synckey`；服务游标按精确非负 64 位整数处理，不转为浮点数或行号 |
| 返回上一批 | 按需保存已经访问的游标，拒绝停滞和循环；最多保存 256 个游标，不预留全量数组 |
| 详情界面 | “简介 / 划线 / 想法”三个页签，复用原生正文分页、返回和刷新；错误保留已有内容，切换页签取消旧请求 |

这里只实现读取个人划线和想法，**没有把划线称作书签，也没有实现新建、修改、删除或云端进度写入**。响应上限 128 KiB、单段文字 8 KiB、拼接文档 32 KiB；超过限制明确失败，不静默截断。书目不匹配、无效 UTF-8、控制字符、错误游标或选中窗口内坏记录均不替换旧页。中文、补充平面字符和换行统一有对应回归检查。

本次真实官方服务返回一条划线和两条个人想法；均通过原生解析和 pai-touch 页面验证。具体书目、笔记正文、Key、Cookie 和真实截图只保留在私有验证目录，没有复制进公开文档或测试资源。这不是已购章节正文验证；按用户要求，没有继续尝试先前无法获取的后续章节。

## 性能与内存：不能混用的证据

开发机采用五对交替测量，均保持 C++26、O3；这些数字只代表该合成输入的桌面 Guest 模型/编码开销，不代表 ESP32 帧率。

| 测试 | 旧实现 | 候选 | 范围 |
|---|---:|---:|---|
| 七万次 JSON 单字段查找，中位数 | 44.50 ms | 27.18 ms | 普通字段名直接借用输入，共用批量查找扫描器；临时分配 200,000→0 |
| 一百次划线解析，中位数 | 476.27 ms | 286.60 ms | 256 章、十条末章划线；章节表和 UID 不重复查找，显示字段共用处理循环；输出校验和相同 |
| 五万次图标编码，中位数 | 16.60 ms | 12.89 ms | 调用实际 SDK 编码器；图标不再发送空 TEXT，每个少 28 B，合计 7,080,000→5,680,000 B；普通书架像素逐点一致 |

数字诊断统一使用有界 `to_chars` 编码，保留原有日志字段，不引入通用格式化库或临时堆字符串。256 B 容量、精确有符号/无符号整数、NUL 拒绝及零动态分配有原生检查；未使用以牺牲速度换体积的编译选项，仍为 O3 和 full LTO。

运行诊断通过编译开关启用，不进入普通发布构建。32 KiB 栈、8×1536 B 协程池的实际 AOT 模拟器诊断矩阵观察到栈上界 5,272 B，包含额外 4 KiB 自检；协程同时占用峰值 6，分配失败 0。后续 16 KiB 栈最终候选的 86 项 AOT 诊断（六屏布局、图片、网络失败、取消与笔记边界）观察到上界 5,320 B、协程峰值仍为 6、分配失败为 0。该数值是已测流程上界，不是所有未来输入的最坏栈证明，更不能代替生产堆测量。保留 Wasm/AOT 越界检查；只有后续完整矩阵和真机门槛满足才会调整默认预留。

### 历史：第一版真机候选未被采用

同一 Host `d8789493…`、字体 `121cb206…`，包和账号均为原生路径。代码映射仍为 21×64 KiB，Guest 书架线性内存均为 131,072 B；但 WAMR 默认加载峰值从 **220,332 B 增至 225,746 B**，加载后计数从 49,443 B 增至 50,617 B。因此没有以功能通过替代内存门槛，已经回退原生产包。

整机窗口还观察到 SRAM 稳定占用相同、PSRAM 稳定占用增加 5,432 B，PSRAM 窗口峰值增加 29,060 B。这里只保留一次前后观测，没有把网络/TLS、文件系统和运行顺序差异全部归因于候选；也不把启动墙钟 5.51→6.94 秒称作确定的 CPU 回归。`MEMORY STOP` 的本次窗口最小空闲与普通 `MEMORY` 的启动以来历史最小值分开使用。

AOT 的 64 KiB 页在该平台确实由 PSRAM 分配并映射到指令总线，不能当作免费的 Flash 地址空间。后续栈和代码调整必须一起核对实际映射、线性内存、WAMR 计数和整机两种堆，不能只看安装包字节数或 Wasm 最小页数。

## 复现、早期失败与后续修复

原生检查可按 README 的 C++26 / ASan / UBSan 命令编译 `tests/notes_test.cpp`、`tests/utf8_test.cpp`、`tests/diagnostics_test.cpp`；后两者分别检查逐字节 Unicode 和无堆格式化。`tests/json_lookup_benchmark.cpp` 使用固定合成对象输出查找时间及分配次数。

集成检查使用合成账号和本机 HTTP fixture：在编译时指定 `WEREAD_FIXTURE_PORT`，用 `tests/notes.py` 运行实际 AOT 和解释器包。全部七套依次为 `renewal.py`、`agent.py`、`smoke.py`、`covers.py`、`images.py`、`network.py`、`notes.py`，每种运行时共 86 项；为每个进程提供独立状态目录、控制 socket 和 fixture 端口。`WEREAD_STACK_PROBE=1` 仅用于诊断，不能用其代码大小、帧率或堆数据冒充普通发布构建。

以下为运行时修复前保留的失败记录。该候选已完成普通 AOT/Wasm 共 172 项流程、86 项 AOT 栈诊断及 10 项原生 ASan/UBSan 检查。同固件真机对照发现 16 KiB 候选在真实 S3 AOT 冷启动和重开均触发 `wasm auxiliary stack overflow`，未达到书架完成事件。原版同流程两次成功；已停止原定八次实验（不补样本寻找通过），保留两次失败及被中止的第三次候选启动，并精确恢复原包和全部私有字节。模拟器的 5,320 B 水位不代表真实 URL 的 S3 AOT 路径，当时在旧 Host 上的 16 KiB 方案被否决。48 KiB 独立 S3 诊断包随后完成真实书架与两张封面（5.80 秒），观察到水位上界 4,904 B、协程峰值 4、分配失败 0；这只覆盖已观察路径，不否定先前真实溢出。详情请求之后等待完成日志超时，存在四条日志丢失且自动化未保留超时前画面，原因尚未确认，整项诊断仍失败。已补充异常截图、原始串口记录和测试构造失败时的子进程清理，尚未将这些增强的诊断结果冒充已完成的真机复验。另外补测“直接恢复五个合成 Cookie、二十本书/4,475 B 元数据”的本地 AOT/Wasm 书架路径，两者均通过，线性内存一页并完整释放；它排除的只是该回放输入，不能推翻 S3 异常。

这一早期失败候选实际映射仍为 21 页，但尚未完成请求时 WAMR 已记录加载峰值 225,794 B（原版 220,332 B）；当时不能把其一页 Guest 内存称为可用的性能收益。该阶段最终回退 `model-boundary` AOT SHA256 `99c3940e7bde50d171adfe4b89f0ad9ca9aca3f13410c184578d3b53f97e89f0`，精确核对原包、私有数据和字体，没有刷 Host。该阶段的 16 KiB 和 48 KiB 均为独立候选，不是当时仓库默认值。

后续定位到 **ESP-IDF 的 WAMR 线程管理器把辅助栈隐式分成五份**：声明 16,384 B，主线程实际只有 3,264 B；模拟器未启用相同线程配置。这解释了先前真实 S3 溢出，不能归咎为“模拟器水位已经证明 16 KiB 够用”。修复整体启用上游按需子线程栈策略，保持主线程完整声明栈，不改 ABI、不关闭边界检查、不增加默认缓存；八项专门原生控制/修复回归与四十项启用 pthread 的 libpxa 回归通过。

对同一份曾失败的 `b2b44db1…` AOT，在精确新 Host 上重新登记并完成八次固定真机测量，再验证真实划线/想法。新实验按实际 SRAM/PSRAM 稳定/窗口峰值、Guest 和映射计数判断，WAMR 加载峰值 +5,462 B 单独披露；没有修改旧实验“任何子计数不得增长”的失败结论。配套采用后，仓库默认改为已测的 16 KiB 栈和 8×1536 B 协程池，根源码重建 AOT 与实测文件逐字节相同。旧 Host 不能直接运行此默认包。

大批量笔记同步解析的真机最长回合尚未得到上界；书签及笔记写入、离线、完整云端位置映射等仍未实现。48 KiB 旧诊断的详情超时仍保留为未确认原因的失败，新版普通构建的真实详情通过不等于已证明该超时的具体成因。最终安装、会话与数据保留说明以 [新报告](runtime-stack-20261017.zh-CN.md) 为准。

发布符号裁剪的额外本地候选没有减少 AOT 元数据，也没有证据证明加载堆收益，未采用。当前可用功能与限制持续以 README 矩阵为准。
