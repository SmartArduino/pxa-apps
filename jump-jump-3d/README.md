# Jump Jump 3D

An isometric 3D remake of the WeChat mini game *跳一跳* (Jump Jump) built on the
PXA GameRender raster service. Press and hold to charge, release to jump, land
on the next block and try to hit its centre: chain centre hits for 2, 4, 6, 8…
points and collect the bonus blocks by standing on them.

The scene is a faithful reimplementation of the original's rules and look, all
in the Guest:

* the original's three.js scene is an **orthographic camera** at `(-17, 30, 26)`
  looking at `(13, 0, -4)`, so the projection is a fixed 3x3 dot product with no
  perspective divide; `+X` travels to the upper right and `-Z` to the upper left,
  which is why the path is a staircase;
* physics keep the original ratios (`gravity 720`, `vz = 70 t`, `vy = 135 + 15 t`
  in 10-unit blocks, scaled by 1/10): a full charge flies ≈ 2.7 world units and
  the useful charge window is ≈ 0.3 s to ≈ 0.95 s;
* blocks are 1.0 x 0.55 units with a white trim band, bonus blocks appear every
  5-7 landings and are always smaller, the block under the player squashes while
  charging, the next block drops in with a bounce, and the background gradient
  advances one of the original's eight palettes every 15 landings;
* a centre hit within 0.0707 units doubles the chain step (2, 4, 6, 8 … capped
  at 32) and drops a white aim dot on the next block; landing again within
  0.8 s doubles the first step ("好快"); landing off-centre resets the chain to
  1 point;
* the failure paths match the original: landing back on the block you left makes
  the little man tip over the near edge, an overshoot drops him past the far
  block, and either way the result panel appears after the fall;
* bonus blocks: 音乐盒 `+30`, 便利店 `+15`, 魔方 `+10`, 井盖 `+5`, all awarded
  after standing still for two seconds — jumping away cancels them;
* the original's audio is used verbatim: the charge swell layered with its
  sustain loop, the landing `success`, the eight rising `combo` notes for centre
  hits, `pop` when the next block drops in, `fall`/`fall_2` on a miss, `start`
  on restart, and the `sing`/`store`/`water` jingles for the bonus blocks
  (repeating every three seconds while the player keeps standing, like the
  original's `onEnded` timers). The menu theme plays once at startup exactly as
  the original does; `J3_BGM_MODE` can loop it as in-run background music or
  silence it.

## Layout

| Path | Role |
|---|---|
| `main.c` | app lifecycle, GameRender context, speed ladder, clock, input, best-score storage |
| `jump3d_game.*` | blocks, generation, difficulty, flight solver, scoring, bonuses, camera |
| `jump3d_render.*` | orthographic projection, painter triangle runs, block and character meshes, shadows, HUD |
| `jump3d_palette.*` | 32 light rows x 256 RGB565 entries shared by every face |
| `jump3d_audio.*` | permission/audio session, the sample mixer and the channel policy |
| `jump3d_audio_data.h` | generated by `tools/generate_audio.py`: the original sounds as 8 kHz IMA ADPCM |
| `jump3d_font.*` | INDEX8 glyph atlases, three resolution tiers |
| `jump3d_font_data.h` | generated by `tools/generate_fonts.py` |
| `assets/` | app icon (SVG source and rendered PNG) |
| `tools/preview_render.c` | offline harness: runs the draw list through the Host raster kernel and writes PPM frames |
| `tools/preview.sh` | builds and runs the harness |

## Build and run

```sh
tools/app.sh build jump-jump-3d --board pai-touch --source-root local/pxa-apps
tools/simulator.sh service start --profile pai-touch
pxadb package install local/app-output/pai-touch/pxa-jump-jump-3d.pxa --simulator pai-touch
tools/simulator.sh product --profile pai-touch --installed pxa-jump-jump-3d
```

or the fast loop:

```sh
tools/dev.sh sim jump-jump-3d --watch
```

The first launch asks for the optional `audio.playback` permission; the game is
fully playable without it (only the synthesised effects are silent).

## Audio

Boards expose only a Guest PCM stream (`pxa_audio_write_pcm`) and this firmware
registers no audio asset sink, so `pxa_audio_play_asset` is unavailable. The
app therefore ships its own mixer (`jump3d_audio.c`) and the original mini game
sounds decoded into it at build time:

```sh
python3 tools/generate_audio.py                 # downloads res/*.mp3, writes the bank
python3 tools/generate_audio.py --source <res>  # or convert a local copy
python3 tools/generate_audio.py --check
```

Each source is trimmed of leading/trailing silence, high passed at 110 Hz (the
panel speaker cannot reproduce the rumble the mp3s carry, and it only eats
headroom), levelled to a common RMS with a peak ceiling (`TARGET_RMS`,
`PEAK_CEILING`: the original mix differs by up to 26 dB between clips, with the
charge sustain almost inaudible under the charge swell), resampled to
11.025 kHz mono (`--rate`), encoded as IMA ADPCM (four bits per sample,
~199 KiB for all nineteen clips) and emitted as packed 32-bit words. The mixer

* resamples to the session's 16 kHz with a Q16 phase accumulator and linear
  interpolation, so there is no zero-order-hold staircase;
* ramps every voice's gain (~12 ms up, ~12 ms down) so ducking, stops and
  retriggers never click;
* sums seven channels through a soft-knee limiter instead of hard clipping;
* keeps `success` and the `combo` notes on separate channels, so the original's
  layering survives;
* keeps each clip's decoded peak inside a checked band (the test asserts every
  clip lands between 0.24 and 0.73 of full scale and never flat tops, which is
  what caught a signed/unsigned underflow in the ADPCM step index: quiet
  passages used to wrap to the coarsest step and hiss).

The bank order is pinned against the clip enum with a compile-time assertion.

## Glyph tiers

`tools/generate_fonts.py` emits three tiers (compact / standard / large) of the
score digits, the latin labels and the Chinese labels. The renderer selects the
tier from the render-target height and always draws at scale 1, so text is
never resampled by a fractional factor — a half-resolution target uses the
compact tier and stays crisp after the Host's 2x upscale. Atlases are laid out
in multiple columns to respect the 256 pixel texture limit, and the largest
atlas is pinned against the upload scratch size at compile time.

## Offline rendering harness

The simulator cannot screenshot a GameRender frame (the game output goes to the
panel instead of the LVGL layer), so the app ships a harness that renders the
*real* draw list with the *real* Host raster kernel and writes one PPM per
frame:

```sh
local/pxa-apps/jump-jump-3d/tools/preview.sh --auto 6 --out /tmp/jump3d
local/pxa-apps/jump-jump-3d/tools/preview.sh --shots 8 --shot-charge 0.72 --out /tmp/fly
local/pxa-apps/jump-jump-3d/tools/preview.sh --hold --shots 4 --out /tmp/charge
local/pxa-apps/jump-jump-3d/tools/preview.sh --auto 3 --kind 3 --out /tmp/music
```

* `--auto N` plays `N` jumps that land exactly on the next block centre (an
  optional `--error` adds an offset for near-miss tests);
* `--shots N --shot-charge T` captures a single jump frame by frame;
* `--hold` captures the charge squash instead of the flight;
* `--kind N` forces the next block type (`1` box, `2` cylinder, `3` music box,
  `4` store, `5` manhole, `6` Rubik's cube).

`--width/--height` let the same harness check other panels without touching the
app.

## Gameplay tests

`tools/package/test_guest_sdk.sh` builds and runs
`sdk/guest-c/tests/pxa_jump3d_game_test.c`, which covers deterministic block
generation, the centre-hit ladder and its 32 point cap, off-centre resets, the
quick-jump doubling, both failure paths, the stay bonuses, and that the
difficulty ramp keeps every block reachable.

## Rendering notes

The Guest only projects and emits; the Host paints. One frame is a clear, a
gradient background, a soft shadow per block, one colour run per block face
group, the little man, the ripple rings and the HUD:

* colour runs batch consecutive triangles that share a palette index, so a whole
  block is 2-5 `TRIANGLE_BATCH` records;
* faces are back-face culled and sorted far to near by hand — no depth buffer is
  allocated or cleared, and painter polygons never touch one;
* lights are per vertex, so the Host interpolates them across each polygon:
  cylinders and the little man get smooth Gouraud shading from 18 and 12
  segments instead of flat strips;
* the 32-light palette (uploaded once as a lit palette) supplies every shade:
  the flat `31/25/23` face lighting of the original and the smooth gradients on
  cylinders and on the little man;
* soft shadows use the Host's fixed 75% alpha blend with two procedurally
  generated shapes: a rounded square under boxes and an ellipse under round
  blocks, each drawn twice (a wide spread plus a tighter, darker contact core)
  with an 8x8 ordered dither between palette greys; the result scrim uses the
  same blend with a solid texel, and a Host without that capability falls back
  to solid shapes;
* zero-area polygons are dropped before submission because the Host rejects a
  whole list for one degenerate triangle;
* the render target follows the panel size with an adaptive ladder that only
  reacts to the Host raster cost. The panel path (compose/rotate/flush), not the
  raster, is the ceiling at 1x on both boards, so the cap sits above both: a
  scale is dropped only when four consecutive windows rasterize slower than
  40 ms, and a sharper step is tried after 20 windows below 20 ms only if that
  scale has not already blown the cap. That keeps esp32s31-korvo-1 at scale 0
  (800x480, 27 ms raster, ~29 fps presented) and pai-touch at scale 0 (296x240,
  12 ms raster, ~31 fps) instead of trading resolution away for no frames. The
  interface metrics and the glyph tier scale with the target, so the HUD, the
  popups and the result card stay readable in every mode. `J3_FORCE_SCALE_SHIFT`
  overrides the ladder for benchmarking (`0` = native, `1` = half);
* every clock tick submits a frame. An optional static-frame skip (`J3_SKIP_STATIC_FRAMES`)
  hashes the scene and drops unchanged frames to save power, but it is off by
  default because the panel flush is the pipeline's real ceiling and a skipped
  frame makes display FPS meters read zero;
* `J3_PERF_LOG` prints
  `j3 perf ticks frames raster_us covered scale N canvas WxH` every five
  seconds, which separates a slow Host loop from App-side work and shows what
  the ladder saw before it moved;
* the frame is never cleared: the background bands tile the target exactly, and
  on a GameRender surface every written pixel costs the Host a store into
  DMA-mapped PSRAM, so a full-frame clear would only be overwritten one command
  later. Measured on pai-touch, dropping the clear removed 11 ms from a 1x
  frame;
* the sky gradient lives in the palette's light rows (one palette index per
  background scheme, row 0 = the top colour, row 31 = the horizon) and is drawn
  as a single painter run, so every span fills with one store instead of the
  general triangle rasteriser's per-pixel edge and attribute work. That took the
  sky from 12.8 ms to 6.0 ms on pai-touch at 296x240;
* the little man's culling follows his pose: heading, squash and tumble are
  applied to the surface normal before it is tested against the camera, and the
  open bottom of the body tube is capped when its normal faces the camera, so no
  face disappears when he jumps in another direction or flips.

Measured with `tools/preview.sh` on the same workload (12 frames, min of 8
kernel runs each): 582 -> 251 us at 296x240 and 97 -> 72 us at 148x120, with
the same visual result. Routing the sky through the painter run and dropping
the clear took the same harness from 2137 us to 855 us at 592x480.

On pai-touch the Guest reports `j3 perf ticks frames raster_us covered scale N
canvas WxH` every five seconds. At native 296x240 (`scale 0`) the Host raster
now takes 11.7-12.0 ms per frame and the board holds **1x at ~31 fps with zero
dropped frames**; the board's own overlay reports the panel flush at 24-27 ms,
so the display path is again the ceiling. Before this pass the same native mode
rasterized in ~29 ms and ran at ~18 fps: an 11 ms full-frame clear that the sky
immediately overwrote, plus 13 ms of sky drawn through the general triangle
rasteriser.

The Host raster itself carries three changes that every GameRender App shares:

* `fill_rgb565` peels the leading pixel and then writes 32-bit pairs. Rows are
  only 2-byte aligned, and one store per two pixels instead of one per pixel is
  what the uncached GameRender targets feel most;
* `draw_quad` recognises whole-pixel axis-aligned flat rectangles (backgrounds,
  bands, panels - the shape the band prefill also looks for) and fills them row
  by row, skipping the general triangle path's per-pixel edge and attribute
  work. Quads with fractional edges keep the existing path, so no App's output
  changes: a regression render at 592x480 is byte-identical to the frame
  produced before the change;
* the CLEAR command only memsets the depth buffer when the list declares
  `PXA_RASTER_CAP_DEPTH_CUTOUT`, instead of for every list that does not use
  coverage masks.

Measured with the offline harness at 296x240: four full-screen flat quads
217 -> 57 us (3.8x), four painter quads 35 us, and a normal game frame
unchanged at 145 us. On esp32s31-korvo-1 (200x120 probe canvas) the same four
quads cost 2784 us through the general path against 1197 us on the rect fast
path (2.3x), which matches the painter path's 1260 us.

GameRender targets are now allocated from *cached* PSRAM instead of the
DMA-mapped pool, with one `esp_cache_msync` (C2M) per frame before the frame is
handed over so the PPA compose, the panel DMA and the direct scanout paths all
read coherent data. Cached stores are what the raster wants: on
esp32s31-korvo-1 a full 800x480 fill through the rect fast path went from
50 ns/pixel to **13 ns/pixel**, and a painter fill of the same target costs
29 ns/pixel. The whole frame followed: the raster went 26.8 -> ~23 ms and the
compose/present path 34.7 -> 23.2 ms, with the display still at ~28 fps and
zero dropped frames (the panel wait is now the limit). Probed at 1x on the same
board, four full-screen quads cost 5149 us on the rect fast path against
31735 us through the general triangle path - 6.2x for identical coverage.

Two board-level notes that bound this further. First, the DMA-mapped PSRAM pool
that GameRender targets used to come from is several times slower to write than
cached PSRAM, which is why `fill_rgb565` and the rect fast path were tuned for
32-bit stores and why the allocation moved to cached memory with a per-frame
`esp_cache_msync`. The pai-touch firmware needs a flash to pick both up; its
panel path (software rotation plus SPI flush, 24-27 ms) is then the ceiling
again.

Second, the Host's banded-background prefill is not worth using as it stands.
`PXA_ESP_RASTER_BACKGROUND_BANDS` is 16 and `prefill_raster_background` only
accepts a list that *starts* with flat-quad bands tiling the whole target, so
the App tried submitting exactly that shape (no clear first, 16 full-width
bands). On esp32s31-korvo-1 the resulting `FillRasterBands` costs about 63 ms
for 16 blocking `ppa_do_fill` calls at 800x480, against ~20 ms for the painter
run that draws the same gradient, so the sky stays on the painter path and the
prefill is left unused (pai-touch registers no `fill_bands` callback at all).
A single PPA fill per band is dominated by per-call overhead here; filling the
gradient in one or two PPA passes, or moving the target into cached memory,
would be needed before the accelerator wins.
