# 音效延迟实测（2026-10-12）

确实存在偶发明显延迟。Maze Evil 把一个音效的多个声部当作并行音源提交，但现有 `play-tone` 混音器在**同一个会话内按 FIFO 顺序播放**。旧声音会挡住新声音，延迟参数也在前一个声部结束后才开始计时。安静时的首声延迟与音效叠加时的排队延迟必须分开看。

本轮是检查与测量，**没有修改现有音频 ABI、FIFO 语义、游戏声音资源或触发规则**。增加了默认关闭的诊断开关、可复现的设备测试与分析程序，修复 C++ SDK Audio 示例漏声明 `permission` 服务的问题。尚未修复的游戏声部播放问题及建议见后文。

## 真机结果

设备为 `/dev/ttyACM0` 的 pai-touch，296×240，序列号末尾 `d5:d4:f0`。游戏为设备原有 Maze Evil 0.1.7，固定种子与初始视角，148×120 RGB565、2 倍显示、33 ms 游戏周期。三个独立启动分别测试：六次孤立开枪（间隔 1.2 s，按住 60 ms）、八次连续开枪（间隔 600 ms，按住 60 ms）、四次较长点按（间隔 1.2 s，按住 200 ms）。

计时使用设备单调时钟，起点为逻辑触摸释放的设备采样时间；不使用串口 ACK 时间。UART 终点为发送第一包非静音 PCM 到 JL701 之前的时间，**不是扬声器出声时间**。物理触摸传感器、USB 输入传输、协处理器解码/缓冲与扬声器声学延迟不在范围内。

| 阶段 | 样本数 | 均值 | 最小—最大 |
| --- | ---: | ---: | ---: |
| 释放采样 → 第一开枪声部提交 | 18 | 18.02 ms | 3.79—36.24 ms |
| 第一开枪声部提交 → 开始混音 | 18 | 3.00 ms | 0.77—16.29 ms |
| 安静场景提交 → 首包非静音 UART | 10 | 1.13 ms | 1.06—1.20 ms |
| 安静场景释放采样 → 首包非静音 UART | 10 | **21.50 ms** | **6.23—37.40 ms** |

安静场景十次由六次孤立开枪和四次较长点按组成；连续音效时不能把下一条 UART 日志归给新的开枪事件。上面不同集合的均值不能直接相加。六次孤立开枪单独统计为 24.21 ms（12.34—37.40 ms），四次长点按为 17.44 ms（6.23—27.29 ms）。

开火设计是短点按 **UP 后**触发。若从 DOWN 开始感受延迟，还要加入按住的 60 或 200 ms；它与音频排队是两个问题。超过短点按阈值或拖动属于视角操作，不应直接改成 DOWN 开枪而导致转向误射。

完整的 18 次开枪共提交 54 个声部，最终轻量追踪采集到了全部提交与混音开始记录，没有音频命令拒收。后端累计接受数从独立测试结束时的 11 增至 65，累计拒收数保持 3（来自独立测试），物理输出队列拒收数始终为 0。第二声部通常等待约 220 ms，第三声部开始混音前通常等待约 340 ms，随后还要经过它自带的 40 ms 延迟。主观上低频部分会明显晚到。

实际游戏测试没有把“首次声部约 1 秒延迟”自然复现出来。另用真实 C++ SDK 的独立签名测试包，在同一会话先提交敌人提示音、再立即提交开枪音效，确实复现：

| 独立测试场景 | 真机现象 |
| --- | --- |
| 一次开枪 | 三个声部的混音开始等待为 0.71、218.04、337.20 ms |
| 敌人提示音 + 立即开枪 | 枪声第一声部等待 **998.21 ms**，另外两个开枪声部返回 `would-block` |
| 开门音效 | 第四声部开始混音前等待 1,176.69 ms，再等自带 280 ms；第五声部被拒收 |

该独立测试证明现有排队机制可以产生约一秒的等待，不把它当作此次游戏场景的延迟分布或最大值。原始数据：[游戏设备记录](audio-latency-20261012/device.json)、[游戏分析](audio-latency-20261012/device-light-analysis.json)、[独立测试记录](audio-latency-20261012/probe.json)、[独立测试分析](audio-latency-20261012/probe-analysis.json)。

## 原生混音器交叉验证

`tests/inspect_audio_timing.cpp` 用实际 Host 混音器和游戏全部 16 种声音配置逐采样渲染。以下是**样本时钟上的排队/时序结果**，不含线程调度、输出设备或听觉测量。

| 音效 | 配置原本的总长度 | 当前 FIFO 渲染总长度 | 丢弃声部 |
| --- | ---: | ---: | ---: |
| 开枪 | 240 ms | 580 ms | 0 |
| 敌人提示 | 500 ms | 1,000 ms | 0 |
| 敌人死亡 | 720 ms | 1,970 ms | 0 |
| 开门 | 580 ms | 1,760 ms | 1 |
| 胜利 | 1,120 ms | 1,300 ms | 2 |
| 玩家死亡 | 1,300 ms | 2,630 ms | 1 |

开枪三个声部原定从 0、0、40 ms 开始，实际从 0、220、380 ms 开始。每个会话只有四个 FIFO 项；五/六声部的配置在批量提交时会超出容量。完整结果：[native-timing.json](audio-latency-20261012/native-timing.json)。

Host 按目前文档中的 FIFO 语义运行；问题是游戏按并行声部使用它。游戏还把非 `unsupported` 返回值都当作 Host 支持，忽略 `would-block`，导致拒收的声部静默丢失。正常 Host 路径并没有启用 Guest 的六帧、120 ms PCM 回退缓冲，不能把该回退缓冲当作这轮首声延迟的原因。

## 输出路径和测量边界

pai-touch 没有直接 I2S codec，声音经 UART 发送给 JL701。当前链路以 16 kHz 单声道、160 样本/10 ms 包的节奏发送。Host 混音以 320 样本/20 ms 为单位，物理输出有三帧固定队列。安静时会唤醒休眠的音频任务，不需要先填满输出队列。已有音频正在播放时仍可能等待正在发送的帧和已混合的输出；要降低剩余实际听觉延迟，需进一步测协处理器的缓冲/播放起点。

第一轮每个 UART 包都用带前缀日志追踪，安静开枪测得约 40 ms；日志量及格式分片会扰动调度，且日志队列发生丢失，**不作为最终数字，也不与轻量追踪相减当作优化收益**。最终改为原始单条日志，仅追踪 UART 活动/静音切换及空闲后的开始，使用有界历史回放并按设备时间戳去重。

系统日志仍有 DROP 提示；最终游戏的 54 次提交、54 次混音开始完整，独立测试的预期接受/拒收数量也完整。分析程序不把重复历史计为新命令，不把连续播放时几百毫秒后的 UART 边沿错误归给新音效。

没有外部麦克风与光学同步采样，不能断言软件阶段的 21.50 ms 就是实际“触摸到声音”。

## 收尾、内存与验证

仅更新应用分区固件，没有修改分区表、NVS、现有应用和存档。临时测试包及其权限/数据已经卸载；原有 Maze Evil 0.1.7 和 Jump Jump 3D 0.1.1 保留。音量等设备设置没有修改，注入指针已释放，测试启动的游戏与性能/内存探针已停止。

设备最终刷回关闭 `PXA_AUDIO_LATENCY_TRACE` 的正常固件，并检查编译命令没有该追踪宏。追踪代码、UART 的诊断状态和日志均不进入普通构建；没有新增默认缓存、任务、队列或混音器缓冲。

正常固件下再次进入游戏并开枪四次，实际 LCD 完成帧率 **30.385 FPS**；截图确认弹药从 24 降至 20：[开枪后](audio-latency-20261012/release-firing.jpg)。该帧率用于确认测量结束后游戏正常，不是音频优化前后对照。

同一 4 秒开枪窗口使用局部 `MEMORY START/STOP`：SRAM 快照占用 280,036 B、本窗口实际峰值 280,112 B；PSRAM 快照占用 2,064,328 B、本窗口实际峰值 2,067,296 B。窗口包含 2,112 B 显示性能探针，截图在窗口外；原始数字见[普通固件检查](audio-latency-20261012/release-game-check.json)。STOP 返回 `minimum_scope=boot` 表示随后恢复历史最低值统计，其前面发出的内存数据仍是此次局部窗口。

混音器仍为 8,640 B 固定 SRAM，音频混音任务栈仍为 4,096 B；流式音乐 PCM 环仍为 16,392 B PSRAM（含分配记账）。本轮没有音频算法改动，因此不宣称内存/帧率改善，也不把不同启动、应用目录或诊断固件间的堆差额当作收益。运行峰值与历史高水位、首次启动峰值分别看待。

- ESP Host 原生回归整套通过，包括音频背压、生命周期、共享输出与设备节奏检查。
- 核心 mixer/buffer/playback/notification 四项重新构建并全部通过。
- 分析程序四项测试通过，覆盖设备时钟、连续音频归属、FIFO 槽复用、历史回放去重。
- 正常/诊断固件均成功构建，设备验证全部声音经实际 SDK 和 Host 输出链路执行。
- SDK Audio 示例补上 `permission` 服务声明；独立测试包使用相同初始化流程，实际通过授权、打开会话、提交 graph 和播放三个场景。未声明的服务不能仅靠 Manifest 的 permissions 列表取得。

## 后续优化方向

优先解决短音效与流式 PCM 共用同一个 FIFO 的语义问题：流式 PCM 保持有序、短音效用有界并行声部，以提交/同组起点为基准计算 delay，并明确同轨替换、优先级、超额拒收与停止行为。游戏应处理拒收，避免排队后播放已经过时的提示。可以复用现有 Host prepared sound/track 路径，也可以在当前固定内存预算里提供并行 tone 能力；具体采用哪种须继续验证 CPU、内存及原音色。

不建议靠增大 FIFO 或加大 PCM 预填充解决：前者容纳更多旧音效，后者增加首声等待。亦不建议直接 flush 所有声音：那会切断其他音效，且已混合的设备缓冲不能按声部回撤。

其他游戏的代码检查发现 Pixel Dungeon 会首次加载资源，且待播队列会在首个未完成加载处停住；Jump Jump 有部分声音预加载，八项共享缓存也可能因替换发生冷加载。这些是值得测量的冷路径，**本轮没有实测它们的延迟**，不能由 Maze Evil 的结果推广。协处理器内的实际播放延迟同样仍待声学/硬件采样验证。

## 复现

在 pxa-projects 工作目录使用 ESP-IDF 环境；诊断开关要作为 `idf.py` 全局 `-D` 参数传入，不在 `tools/firmware.sh` 的 action 后重复传 `-D`：

```sh
idf.py -C firmware -B build/firmware/pai-touch \
  -DPXA_BOARD=pai-touch -DPXA_AUDIO_LATENCY_TRACE=ON reconfigure
bash tools/firmware.sh pai-touch build
bash tools/firmware.sh pai-touch app-flash --port /dev/ttyACM0 --baud 460800
python3 local/pxa-apps/maze-evil/tests/measure_audio_latency.py \
  --port /dev/ttyACM0 --output /tmp/maze-audio-trace
python3 local/pxa-apps/maze-evil/tests/analyse_audio_trace.py \
  /tmp/maze-audio-trace/report.json

# 测完关闭追踪，重新构建并只刷应用分区。
idf.py -C firmware -B build/firmware/pai-touch \
  -DPXA_BOARD=pai-touch -DPXA_AUDIO_LATENCY_TRACE=OFF reconfigure
bash tools/firmware.sh pai-touch build
bash tools/firmware.sh pai-touch app-flash --port /dev/ttyACM0 --baud 460800
```

独立测试包源代码位于 `tests/audio-latency-probe`，使用 C++ SDK 初始化与同一组 `sfx_profiles.h`，按钮依次测试开枪、提示音加开枪、开门。需要授权临时包的媒体播放权限；每次测试后等待至少 2.4 s，测完卸载此临时包。基准脚本不会录制主机麦克风或改变音量。
