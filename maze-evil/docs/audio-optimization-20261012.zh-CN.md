# 音效并行播放与简化实现（2026-10-12）

本轮针对 Maze Evil 音效晚播的已确认原因：游戏把一个音效的多层合成声音分别送入 Host 的顺序 FIFO。现在 Audio 0.9 提供一次提交、共同采样时钟起播的音效组，ESP 和 SDL 共用同一混音器。Maze Evil 0.1.8 使用这个接口，并删除 Guest PCM 兼容混音器，需要 Audio 0.9 固件。

## 原因、收益、内存与验证

| 修改 | 原因与收益 | 内存变化 | 验证 |
|---|---|---|---|
| `AudioSession::effect(span, track)` | 整组验证和提交；层之间的延迟从组起点计算；枪声从 3 次跨边界调用变为 1 次 | SDK 只使用 116 B 的短期栈命令，无堆分配或常驻缓存 | SDK 编码、参数边界、服务整组拒收；16 组真实游戏配方 |
| 复用 PCM 槽位的并行组 | 修正层串行、被前一音效阻塞及中途丢层 | 混音器固定存储 8640 → 8592 B；PCM 单独使用仍有每会话 4 帧容量。新增后端回调占服务表空间，整体由真机核对 | PCM FIFO、空闲会话、复用槽位、并行延迟、失败原子性 |
| 命名轨道替换及停止 | 不积压失去时效的事件；满容量时可以替换同轨声音 | 同一固定槽位，无额外待播放队列 | 满容量替换、独立组拒收、停止、flush、close、暂停 |
| 位置决定的振荡器和噪声 | 输出拒收后可准确重试；不新增每层回滚快照；频率步长、增益、包络倒数在接收时计算 | 无额外回滚缓冲；原音频任务栈容量不变 | 分块与逐样本输出一致；拒收后重试波形逐字节一致 |
| 删除游戏兼容 PCM 引擎 | 避免应用维护合成、排队估算和 Host 合成两套实现 | `game_audio_t` 2320 → 24 B；Guest 线性内存上限仍为 1 MiB，不将结构缩小等同于物理内存回收 | 游戏原生检查，SDL 真实输入与双指操作，真机 18 次开火 |
| 测量按设备时间划分场景 | LOGSUB 会重放历史；避免将之前的音效计入新测试 | 仅测试工具变化 | 6 个分析器检查，保留旧格式支持 |

预计算减少了采样热路径上的运算，但尚未单独测量各项 CPU 收益。FPS 不以原生采样时钟测试推断。

## 实测结果

所有 16 组配方的层起点与持续时长均符合设计，0 丢层。可复查 [新路径](audio-optimization-20261012/optimized-native-timing.json) 和 [FIFO 路径](audio-optimization-20261012/legacy-native-timing.json)。例如：

| 音效 | FIFO 实际时长 | 并行组实际时长 | 并行组层起点 |
|---|---:|---:|---|
| 枪声 | 580 ms | 240 ms | 0 / 0 / 40 ms |
| 敌人提示 | 1000 ms | 500 ms | 0 / 160 / 300 ms |
| 开门 | 1760 ms，丢 1 层 | 580 ms，完整 5 层 | 与配方一致 |
| 死亡 | 2630 ms，丢 1 层 | 1300 ms，完整 5 层 | 与配方一致 |

pai-touch `/dev/ttyACM0`，296×240，序列号 `a4:cb:8f:d5:d4:f0`，真实 C++ SDK 测试应用：

- 单独枪声：提交 → Host 开始渲染 1.138 ms。
- 敌人提示后立即开火：两个组都完整接受；枪声渲染等待 16.657 ms。之前同一组配方使用 FIFO 的测试中，枪声首层等待 998.212 ms，另有两层拒收。
- 开门：全部 5 层一次接受，提交 → 渲染 0.920 ms。

数据见 [探针分析](audio-optimization-20261012/optimized-probe-analysis.json)。旧值来自 [此前诊断](audio-latency-20261012.zh-CN.md)。两轮固件还包含工作区其他改动；具体调度耗时不是严格同版本的 CPU 对比。FIFO 等待消除同时由同一原生混音器的两种路径验证。

游戏分三次启动，固定开局视角，6 次间隔 1.2 s 的短按、8 次间隔 0.6 s 的短按、4 次间隔 1.2 s 的长按，共 18 次开火，18 组全部接受，0 组拒收；三层枪声作为完整组播放。提交 → Host 渲染平均约 1.058 ms，范围 0.963–1.307 ms。

10 次空闲枪声中，松手设备采样 → 首个非零 UART 块平均 22.2105 ms，范围 9.065–36.553 ms；此前对应指标为 21.5044 ms。空闲路径未证明显著改善，改善集中于重叠音效的排队。快速场景不把下一个 UART 边沿归属于新枪声。数据见 [游戏分析](audio-optimization-20261012/optimized-device-analysis.json)。

以上均为软件时间，未录制麦克风，不包含协处理器解码/缓冲与扬声器起声。开火仍在短按松手后发生，按住的时间另计。

## 正式构建的帧率与内存

修改前同设备正式构建、固定开局 4 次开火、约 4 秒窗口，实际 LCD 完成帧率 30.41472 FPS。稳定 SRAM 占用 286280 B，窗口峰值 286368 B；PSRAM 稳定 2092840 B，窗口峰值 2093440 B，含双方相同的 2112 B 帧探针。

修改后关闭诊断的正式构建，使用同一个 4 次开火、约 4 秒测量窗口：

| 指标 | 修改前 | 修改后 |
|---|---:|---:|
| 实际 LCD 完成帧率 | 30.41472 FPS | 30.37655 FPS |
| SRAM 稳定占用 | 286280 B | 279936 B |
| SRAM 窗口峰值 | 286368 B | 280060 B |
| PSRAM 稳定占用 | 2092840 B | 2063720 B |
| PSRAM 窗口峰值 | 2093440 B | 2068984 B |

帧率差约 -0.13%，按本次短窗口结果视为持平，不宣称提高 FPS。稳定占用和绝对峰值均未增长。期间工作区还有输入法改动，整体内存下降不能全部归因于音频；可明确归因的是混音器存储减少 48 B、游戏状态减少 2296 B，以及删除兼容合成代码。Guest 线性内存上限、帧探针、显示队列和音频任务栈容量未增加。

[前后原始正式报告](audio-optimization-20261012/release-comparison.json) 另列启动期间的总空闲和历史最小空闲记录，不把这些值标作本轮游戏窗口的运行峰值。新构建的预算历史峰值已重置，不能与旧构建累计值比较。所有 PXA 分配拒绝及失败计数均为 0。设备截图：[开火画面](audio-optimization-20261012/device-firing.jpg)。临时探针已卸载，现有两款游戏和数据保留，设备上 AudioTrace 已关闭。`MEMORY START/STOP` 的窗口最小空闲值用于本轮运行峰值；预算历史峰值和首次初始化记录另列，不替代窗口值。

冷重启后，在 `PACKAGE run` 前开启独立内存窗口，等待标题页加载 3 秒后结束窗口；停止应用，再做两次相同的重复启动：

| 激活阶段 | SRAM 窗口绝对峰值 | PSRAM 窗口绝对峰值 |
|---|---:|---:|
| 首次初始化 | 285596 B | 2745324 B |
| 重复启动 1 | 281296 B | 2783668 B |
| 重复启动 2 | 281296 B | 2783620 B |

这是包含加载与初始化的真实窗口峰值，与前述游戏运行窗口分开；没有把启动前的历史最小空闲作为这个窗口的峰值。两次热启动停止后 SRAM 空闲均为 43771 B，PSRAM 空闲差 60 B。三次退出均显示 Guest 线性内存为 0、事件内存为 0、AOT 映射已释放，WAMR 保留同样的 416 B 运行时记录。首次启动后系统共用缓存与音频任务保留，不将其误判为重复启动泄漏。数据见 [生命周期原始记录](audio-optimization-20261012/release-lifecycle.json)。

新版本实际 Guest 线性内存峰值 475136 B，上限仍为 1 MiB；执行代码映射请求 112480 B，实际映射 131072 B；WAMR 动态统计峰值 229254 B。不同统计类别可能重叠，不相加推导总占用。[运行时原始计数](audio-optimization-20261012/runtime-memory.json) 保留三次激活记录。旧版没有对应的同窗口细分类记录，因此不声称这些类别的独立改善幅度。帧缓冲、显示队列、Guest 的渲染和命令路径未改动；本轮不增加深度缓冲或命令缓存。

## 行为与限制

游戏按武器、敌人、场景、玩家分为四个替换轨道。同类新事件会结束旧事件的未提交尾部；不会保留所有敌人的同时独立尾音。这是固定预算下的明确选择。已送往物理输出队列的样本无法撤回。本轮没有改变协处理器协议、输出块长度或物理队列容量，也不宣称解决全部声学延迟。

Audio 0.9 一组最多 8 层；Host 目前每会话 4 个共用槽位。轨道标识 0..5 不代表保证六组同时播放。PCM 和并行组共同使用槽位，应用必须处理 `WOULD_BLOCK`；该错误不接受任何一层，也不保留待重试事件。固定预算和背压语义见 SDK/ABI Audio 0.9 规范。

新路径的白噪声改为按位置生成的确定性整数哈希；频率、增益及包络配方保留，噪声的具体样本序列改变。旧 FIFO tone 的噪声序列保持原实现。没有进行主观听感或声学频谱评价。

## 重复验证

在项目根目录运行：

```sh
bash firmware/components/pxa/tests/test_host.sh
bash deps/pxa-system/tools/package/test_guest_cpp.sh
bash local/pxa-apps/tests/native/run.sh
ctest --test-dir build/libpxa-adapter-tests \
  -R '^pxa_(core|audio_(mixer|buffer|playback|notification))_test$' --output-on-failure
python3 local/pxa-apps/maze-evil/tests/test_audio_trace.py
```

原生配方诊断 `inspect_audio_timing.cpp` 链接 `audio_mixer.c`；无参数使用 FIFO，加任意参数使用并行组。C++ SDK 真机探针源在 `tests/audio-latency-probe/`；授予其音频权限后使用 `measure_audio_probe.py --port /dev/ttyACM0 --output <目录>` 测量三个场景。真机软件时间测量使用 `PXA_AUDIO_LATENCY_TRACE=ON` 的应用分区固件及 `tests/measure_audio_latency.py`，随后使用 `analyse_audio_trace.py`。正式帧率/内存使用关闭诊断的固件运行 `measure_input_latency.py --repeat 1 --modes firing`，保留游戏和用户数据，移除临时探针。诊断值与正式帧率不能混用。

完整 SDK、Host 原生检查和游戏模拟器操作检查已通过。全局规范检查目前受并行新增的 `pxa-ime.json` 与旧规范库存数量不匹配影响；排除该新文档后，其余规范（含 Audio 0.9）与 golden vectors 检查通过。未改动输入法规范或覆盖其他工作区改动。
